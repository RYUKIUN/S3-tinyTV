# S3 Next-Gen JPEG Stream — Project Structure and Explanation (v4.0)

## 1. Project overview
This project is a WiFi-based screen mirroring system built around an ESP32-S3 and a small ILI9341 TFT display. A Windows PC captures a monitor (normally a virtual display), resizes it to 320×240, JPEG-compresses each frame as **one complete image**, and sends it over UDP to the ESP32-S3. The ESP32 reassembles the frame, decodes it block by block directly into a PSRAM framebuffer, and pushes the finished frame to the display using DMA.

As of **v4.0** the firmware is a **pure ESP-IDF** project (no Arduino core, no PlatformIO) and decodes with Espressif's `esp_new_jpeg`. The earlier four-tile pipeline has been replaced by full-frame transport.

The design is optimized for real-time display and uses:
- Dual-core ESP32-S3 operation
- PSRAM-backed display framebuffers and explicit buffer ownership between tasks
- Full-frame JPEG transport with block-mode decode
- UDP chunk reassembly with strict packet validation
- Adaptive JPEG quality control on the PC side
- Optional touch input (compile-time switch)
- HTTP OTA firmware updates

## 3. Build and configuration files

### CMakeLists.txt (root)
The minimal standard ESP-IDF project file. It includes the IDF project CMake and names the project `s3_nextgen_jpeg`, which is also the name of the output binary (`build/s3_nextgen_jpeg.bin`). It does not need to change when source files are added.

### main/CMakeLists.txt
Registers the `main` component. Every `.cpp` file must be listed in `SRCS` here — ESP-IDF does not glob sources — together with the `REQUIRES` list of IDF components (`esp_wifi`, `esp_netif`, `esp_http_server`, `app_update`, `esp_driver_tsens`, `esp_psram`, …) and the two managed components `lovyangfx` and `esp_new_jpeg`. If a build reports "could not resolve component", this is the file to edit.

### main/idf_component.yml
The component-manager manifest. It declares:
- ESP-IDF `>=5.1`
- `espressif/esp_new_jpeg` `^1.0.2` from the Espressif component registry
- `lovyangfx` as a git dependency on LovyanGFX tag `1.2.33`

The first configure needs internet access; afterwards the components are cached in `managed_components/`.

### sdkconfig.defaults
Baked-in Kconfig defaults for the **N16R8** board, merged into `sdkconfig` on the first configure. It sets:
- target `esp32s3`, 16 MB QIO flash at 80 MHz
- the custom OTA partition table
- 8 MB Octal PSRAM at 80 MHz, exposed to the heap through `heap_caps_malloc(MALLOC_CAP_SPIRAM)` (plain `malloc()` deliberately does not fall back to PSRAM)
- 240 MHz CPU, 1000 Hz FreeRTOS tick, dual-core
- Wi‑Fi buffering: software coexistence, 16 static / 32 dynamic RX buffers, block-ack window 16, UDP receive mailbox of 32 packets
- performance compiler optimization
- UART0 console at 115200 baud, 5 s task watchdog

This file replaces the old `platformio.ini`.

### partitions_16MB_ota.csv
Flash layout: `nvs` (20 KB), `otadata`, two 1.5 MB app slots (`app0`, `app1`) for OTA, and a large `spiffs` partition that the firmware does not currently use.

### requirements.txt
Python dependencies for the PC-side sender: `opencv-python`, `mss`, `numpy`, `psutil`.

### settings.json
Stores the last-used `Sharpen`, `Debug Mode` and `Enable Touch` slider values for the sender. It is rewritten when a preview window closes.

## 4. PC-side sender

### captureJpeg.py
The Windows sender application. It:
- listens on UDP port 12345 for the ESP's `S3READY` beacon and spawns one process and preview window per discovered ESP
- captures the selected monitor with `mss` in a background thread (portrait monitors are rotated to landscape)
- draws the PC cursor into the frame, and a green ring while a touch drag is active
- resizes to 320×240, optionally sharpens, and JPEG-encodes the whole frame (4:2:0 chroma)
- sends the frame as ≤1400-byte chunks with an 8-byte header, pacing chunks 250 µs apart and frames at a fixed 50 FPS
- adapts JPEG quality to a 25,000-byte frame budget (quality ceiling 80) with immediate, escalating drops and a cooldown before climbing back
- shows four controls (`Sharpen`, `Debug Mode`, `Enable Touch`, `Monitor`) and two overlay modes: ESP stats and PC encoder stats
- turns the ESP's raw touch events into Windows mouse input (`TouchInjector`): tap → click, slide → scroll, hold → drag, with cursor borrow-and-return and a stuck-button watchdog

## 5. Firmware source files (`main/`)

### nexus.h
The central configuration and shared-state header — the "nexus" of the project. It is organized in zones by how likely you are to edit them:
- **Zone 1 — edit before flashing:** Wi‑Fi SSID/password, `WIFI_TX_POWER`, OTA hostname and HTTP port, display SPI pins and clock, touch pins, `TOUCH_USE_IRQ`, `TOUCH_FEATURE_ENABLED`
- **Zone 2 — hardware/memory tunables:** screen size, UDP chunk size, `MAX_JPEG_FRAME` (35 KiB), number of JPEG slots and display buffers
- **Zone 3 — timing and behavior:** packet/assembly timeouts, Wi‑Fi connect timeout, all touch sampling and calibration parameters
- **Zone 4 — internal plumbing:** pipeline structs (`JpegFrameSlot`, `DecodeMsg`, `DisplayMsg`, `TouchEvent`), FreeRTOS queue handles, shared buffers, cross-core stats and the shared SPI mutex

### app_main.cpp
The firmware entry point and orchestration hub. It:
- creates the SPI mutex and touch queue, initializes the display, NVS and (optionally) touch
- checks PSRAM, initializes the JPEG decoder, and allocates JPEG slots and display framebuffers with graceful fallback to fewer buffers
- creates the four pipeline queues (free JPEG slots, decode, display, free framebuffers)
- brings up Wi‑Fi, starts the OTA server, and creates the FreeRTOS tasks
- registers per-core idle hooks used for CPU-load statistics
- contains `decodeTask`, which pulls a completed JPEG and a free framebuffer, decodes, then hands the framebuffer to the display task (or returns it on failure)

`app_main()` simply returns after creating the tasks; there is no Arduino `loop()`.

### wifi.cpp / wifi.h
Native `esp_wifi` / `esp_netif` station management: NVS initialization (`nvsInit`), Wi‑Fi bring-up (`wifiInit`: 802.11n, 20 MHz, power save off, configurable TX power), reconnect, IP string and RSSI helpers. An event handler keeps the shared `g_wifiOk` flag current.

### network.cpp / network.h
The UDP side of the system, running in `networkTask`, plus `wifiWatchdogTask`.

Responsibilities:
- create and bind the UDP socket (port 12345, non-blocking)
- validate each video packet (header, flags, chunk index/count, chunk length and total size must be mutually consistent)
- track frames per JPEG slot, reassemble chunks, drop frames that exceed the 80 ms assembly timeout, and check JPEG start/end markers
- queue completed frames to the decoder
- handle control packets from the PC (debug stats on/off, touch on/off)
- send the `S3READY` discovery beacon while idle
- send debug stats (FPS, temperature, jitter, decode time, drops, aborts, SRAM/PSRAM, per-core CPU load)
- drain the touch event queue and send touch packets (the socket is only ever used by this one task)
- watchdog: reconnect Wi‑Fi and keep the status line up to date

### jpeg_decode.cpp / jpeg_decode.h
Wraps `esp_new_jpeg` in block mode with RGB565 big-endian output. `decodeJpegFrame()` parses the header (the image must be exactly 320×240), then decodes 16-row blocks into a small aligned internal-RAM scratch buffer and copies each block straight into the target PSRAM framebuffer. It reports the pure decode time for the statistics.

### display.cpp / display.h
Display driver and presentation.

Responsibilities:
- the `LGFX` class configuring LovyanGFX for the ILI9341 (and the XPT2046 when touch is enabled) from the `nexus.h` macros
- boot header and status lines
- `displayTask`: takes a decoded framebuffer, holds the SPI mutex for the entire DMA push, and returns the framebuffer to the free queue when DMA finishes
- "WAITING FOR VIDEO" / "WIFI DISCONNECTED" overlays when packets stop
- feeding the task watchdog

### touch.cpp / touch.h
The input side (compiled only when `TOUCH_FEATURE_ENABLED` is 1).

Responsibilities:
- initialize the XPT2046 on the shared SPI bus, with optional PENIRQ
- 4×4-point bilinear calibration, stored in NVS, with a BOOT double-press to redo it
- sample the panel, debounce, and post DOWN / MOVE / UP events to a queue
- leave all gesture interpretation to the PC sender

### ota.cpp / ota.h
A tiny `esp_http_server` endpoint (`POST /update` on port 3232) that streams a firmware image into the inactive OTA partition, validates it, switches the boot partition and reboots.

### port.h
The whole "porting layer" left over from the Arduino version: `millis()`, `micros()`, `delay()` and `constrain()` implemented over `esp_timer` and FreeRTOS, so the rest of the code did not need rewriting.

## 6. How the project actually works

### Data flow from PC to display
1. The PC captures a frame with `mss` and resizes it to 320×240.
2. The frame is JPEG-compressed as one image and split into UDP chunks.
3. `networkTask` validates and reassembles the chunks in a JPEG slot.
4. `decodeTask` takes a free display framebuffer and decodes the JPEG block by block into it.
5. `displayTask` pushes the framebuffer to the ILI9341 by DMA, then returns it to the free queue.
6. The user sees live output on the ESP-connected TFT display.

### Data flow in reverse
- While the panel is touched, the ESP sends raw touch events to the PC (and debug stats, when enabled).
- The Python sender maps them to Windows mouse actions.
- The PC can be controlled from the connected display, and can switch touch reporting off at the source.

## 7. Core architecture ideas

### Dual-core task structure
- Core 0: `networkTask`, `displayTask`, `wifiWatchdogTask`, `touchTask`, HTTP OTA server
- Core 1: `decodeTask`

Network receive and JPEG decode never compete for a core.

### Explicit buffer ownership
Two free queues own the buffers: one for JPEG slots, one for display framebuffers. A JPEG slot is owned by `networkTask` while it fills, by `decodeTask` while it decodes, then returned. A framebuffer is owned by `decodeTask` while it is written and by `displayTask` until its DMA transfer completes. Nothing is copied whole-frame, and no buffer can be reused while still in use.

### Whole-frame failure handling
If any chunk is missing, a packet is malformed, the JPEG markers are wrong, or decoding fails, the frame is discarded and its buffers are returned. The panel keeps the last successfully presented frame rather than showing partial or corrupt pixels.

### PSRAM and SRAM placement
Display framebuffers (3 × 150 KiB) live in PSRAM. The first two JPEG slots prefer internal SRAM because the decoder reads them on the hot path; the decoder's 10 KiB block scratch is internal SRAM too.

### Adaptive encoding on the PC side
The sender measures each frame's size against a 25,000-byte budget and adjusts quality in real time: drops are immediate and escalate on consecutive overflows; recovery is slow and only after a cooldown.

### OTA and centralized configuration
After the first USB flash, firmware updates are a single `curl` upload. Key settings are centralized in `nexus.h` so adapting to different wiring or networks does not require changing logic in several files.

## 8. Critical design note: the "nexus" concept
The most important architectural idea in this project is that nearly all configuration and shared state are centralized in [main/nexus.h](main/nexus.h). This includes:
- Wi‑Fi, TX power and OTA settings
- display and touch pin assignments
- screen size, chunking and buffer counts
- timing and touch tuning values
- global FreeRTOS objects
- shared structs for network/decode/display communication

This keeps the firmware easy to maintain and easy to adapt to different hardware layouts without touching the logic in many source files.

## 9. Summary
This project is a full real-time streaming pipeline combining:
- a PC capture/encode/send application
- a Wi‑Fi UDP transport with full-frame JPEG chunking
- a dual-core ESP32-S3 decode engine built on pure ESP-IDF
- a DMA-driven display path
- optional touch interaction that turns the panel into a PC mouse

The idea is simple but technically rich: take screen content from a PC, compress and stream it over Wi‑Fi, decode it on an ESP32-S3, and display it on a small TFT panel with minimal latency, with strict buffer ownership and adaptive quality keeping it stable. It is a performance-oriented embedded system built around real-time constraints, not just a demo.
